# RULES.md — 機制紀律七條

> **這份文件規範的是「守門機制」本身，不是程式風格。**
> 本 repo 是單人 portfolio，由一連串互不相識的 session 接力開發。沒有同事會在 code review 時說「這個檢查根本沒跑過吧」。
> 唯一能扮演這個角色的，是**機制本身要能證明自己活著**。以下七條就是「一個檢查有沒有資格被信任」的門檻。
>
> 適用對象：任何新增的 CI job、guard script、測試、lint 規則、pre-commit hook、文件對帳閘。
> 現有實作見 [`scripts/gates/`](../scripts/gates/)，兩支閘（文件漂移、spec 台帳）就是照這七條寫的，可以直接抄。

---

## 為什麼需要這份文件

這個 repo 已經示範過「機制存在但不生效」的所有經典形態，四種都在同一個小 repo 裡同時發生：

| 現象 | 事實 |
|---|---|
| 定義完整但從未執行的 CI | `.github/workflows/pr-checks.yaml` 五個 job 寫得很漂亮，`gh run list --workflow pr-checks.yaml` 回傳 **0 筆**——這個 repo 全部直推 main，零 PR，所以它一次都沒跑過 |
| 死掉的進度追蹤 | 兩份 implementation plan 合計上百個 checkbox，**勾了 0 個**，但 P0/P1 早已實作完成並在叢集上跑過 |
| 落後現實的狀態宣告 | `README.md` 首屏（public repo，第一個讀者看到的東西）寫「全專案 spec-only、實作待啟動、`docs/plans/` 仍空」，而磁碟上已有兩份 implementation plan、成套的 Python 實作、以及跑過真資料的 Gold 5 表 |
| 被 path filter 繞過的測試 | 截至 2026-08-10，最近 **11 個 commit 零 CI 覆蓋**——它們改的檔案全部落在當時四支 push workflow 的 path filter 之外 |

這些都不是「有人偷懶」。每一項在寫下的當天都是誠實且正確的。
問題在於：**它們沒有任何機制會在失效的那一刻叫一聲。** 失效是靜默的，所以一路長到今天。

七條規則要防的就是這件事：**讓機制的死亡變成一個會紅的事件，而不是一個沒有人注意到的狀態。**

---

## 第 1 條：閘要有陽性對照

**規則**：任何守門機制，都必須附帶一段可執行的證明——**在它應該紅的情況下，它真的會紅**。這段證明本身要能被跑（CI 或一行指令），不能只是作者口頭說「我試過了」。

**為什麼**：一個永遠綠燈的閘，和一個不存在的閘，對使用者來說是同一件事——甚至更糟，因為它會發出「這裡有人看著」的錯誤訊號，讓後面的人不再去看。

綠燈有兩種：**「檢查跑了，沒發現問題」**，和**「檢查根本沒在檢查」**。這兩者在終端機上長得一模一樣，都是一行綠色的 PASS。唯一能區分它們的方法，就是**故意弄壞一次，看它會不會紅**。你沒做過這件事，就沒有證據說自己屬於前者。

而且這不是一次性的：閘寫對了，半年後有人改了資料結構、改了掃描路徑、改了檔名慣例，閘就悄悄變成後者了。所以陽性對照必須是**可重跑的程式碼**，跟閘一起活著，而不是開發當天的一張截圖。

**怎麼做**：在 `scripts/gates/positive_control.py` 這類 harness 裡，對一份 repo 的暫時副本注入缺陷 → 跑閘 → 斷言 exit code 為 1 → 還原。每支閘至少一組。跑法：

```bash
python scripts/gates/positive_control.py          # 全部；exit 0 = 每支閘都證明會咬人
```

## 第 2 條：陽性對照要指名哪一條斷言炸了

**規則**：陽性對照不能只斷言「exit code != 0」。它必須斷言**是哪一條檢查、因為什麼原因紅的**。實作上：每條檢查配一個穩定的錯誤碼（本 repo 用 `DRIFT001` / `LEDGER003` 這種形式），陽性對照斷言「輸出裡出現 `DRIFT001`」。

**為什麼**：「紅了」跟「因為我想驗的那件事而紅」是兩回事，而且第二種比第一種難得多。

最常見的失敗長這樣：你注入一個矛盾，跑閘，紅了，你很滿意。但實際上是你注入時把 YAML 弄壞了、或是路徑打錯導致腳本 `FileNotFoundError`、或是暫存目錄沒有 `.git` 所以 `git ls-files` 直接爆掉。閘在**注入的副作用**上紅，而不是在**你想驗的規則**上紅。於是你收到一個假的信心：你以為驗過了規則 A，其實只驗到「腳本會 crash」。

這種錯誤特別惡毒，因為它會通過你所有的檢查步驟——你確實跑了指令、確實看到紅色、確實 exit code 非 0。錯的是判準，不是執行。而**壞掉的判準會把後面每一次觀測都染色**。

指名錯誤碼把「紅了」升級成「紅在第 3 條」。這是唯一能區分「驗到了」跟「碰巧紅了」的辦法。

**怎麼做**：閘的輸出格式固定為 `<CODE> <人話說明>`，錯誤碼進 `--json` 的 `codes` 陣列。陽性對照斷言 code 集合，不斷言訊息文字（訊息會改，碼不會）。順帶一提，這也讓「一次注入同時觸發兩條規則」變成可偵測的——期望 `{DRIFT001}` 卻拿到 `{DRIFT001, DRIFT000}` 就是注入手法有副作用。

## 第 3 條：分母不能是空的

**規則**：任何形式為「掃描一組東西，逐一斷言」的檢查，都必須先斷言**掃到的東西數量 > 0**（或 > 某個已知下界）。掃到 0 筆一律紅，不准靜靜通過。

**為什麼**：`for x in []: assert f(x)` 是**恆真**的。空集合上的全稱斷言永遠成立，這是邏輯，不是 bug——所以你不會收到任何錯誤訊息。

實務上分母歸零的方式多到數不完，而且全都不會報錯：glob 的目錄名改了；重構把檔案搬走了；CI 的 working-directory 跟本機不同；`git ls-files` 在 detached HEAD 或 shallow clone 下少抓一半；副檔名從 `.yaml` 改成 `.yml`；有人把掃描根目錄從 `docs/` 改成 `./docs`（在某些 glob 實作下這會少一層）。每一種都讓閘從「檢查全部 spec」變成「檢查 0 份 spec」，而終端機顯示的還是那行綠色 PASS。

換句話說：**掃描型的閘，最可能的失效模式不是判斷寫錯，而是根本沒掃到東西。** 而這個失效模式的預設行為是「通過」。這正好是最壞的方向：假綠讓人停止調查，紅燈只是讓人多花十分鐘。**把失敗方向判反，比 bug 本身貴。**

還有一個延伸：**綠燈本身也有分母**。「所有 spec 都在台帳裡」如果台帳有 44 行而 spec 只掃到 3 份，那也是通過——所以兩邊的數量都要斷言，不能只斷言其中一邊。

**怎麼做**：每支閘開頭先跑 `_assert_denominators()`，任何一個母體為 0 就吐 `*000` 錯誤碼並 exit 1。不要用 `assert len(x) > 0` 混在迴圈裡——要獨立成一條有自己錯誤碼的檢查，這樣第 2 條才驗得出來。

## 第 4 條：圍籬要 fail-closed

**規則**：檢查遇到**無法分類**的輸入時——沒看過的狀態值、格式不符的行、解析失敗的檔案——一律**擋**，不是放行。「我不認識這個」是紅燈的理由，不是略過的理由。

**為什麼**：fail-open 的圍籬有個致命性質：**繞過它的方法就是做一件它沒想過的事**——而「做一件沒人想過的事」正是新功能的定義。所以圍籬會在最需要它的時候（引入新東西時）失效，在最不需要它的時候（重複既有模式時）盡責。這是完全顛倒的可靠度曲線。

具體到本 repo：spec 台帳的狀態欄允許 `已實作 / 已規劃未實作 / 已作廢 / 勘誤層`。如果有人打成 `已實做`（錯字）或 `WIP`，fail-open 的寫法會是 `if status == "已實作": check_evidence()`——錯字直接跳過所有檢查，那一行 spec 從此不受任何約束，而且**看起來還在台帳裡**，比不在台帳裡更難發現。fail-closed 的寫法是先斷言 `status in ALLOWED`，不在就 `LEDGER005`。

同理適用於：解析不了的 plan 檔（不是「跳過」，是紅）、找不到 `git`（不是「用檔案系統 fallback」，是紅）、marker 格式不合（不是「忽略」，是紅）。

**代價要誠實講**：fail-closed 會製造假警報，會在你趕時間時擋你。這是設計上要付的錢。付得下去的原因是——假警報的成本是十分鐘，假通過的成本是一個沒有人知道存在的缺口活了半年。

## 第 5 條：繞過要留台帳

**規則**：任何形式的例外——`# noqa`、`skip_ci`、豁免清單、`--force`、關掉某條檢查——都必須留下**機器可讀、可被清點的紀錄**：豁免項要進一份明列的清單檔（而不是散在各處的 inline 註解），清單長度本身要被斷言或至少被印出來。

**為什麼**：沒有記錄的旁路，比紅燈危險得多。

紅燈是可見的：它擋在那裡，有人得處理它。**無記錄的旁路是不可見的**：它讓紅燈消失，於是所有儀表板都顯示健康，而缺口原封不動地留在原地。你失去的不只是那一條檢查，你失去的是「有多少條檢查被關掉了」這個資訊——也就是失去了評估自己覆蓋率的能力。

第二個理由是趨勢：單一豁免通常是合理的（環境限制、上游 bug、暫時性）。危險的是**豁免數量的成長**。台帳讓「這個月從 3 條變成 17 條」變成一個看得見的數字；散落的 inline 註解讓同一件事變成一種氛圍。

第三個理由更現實：**旁路是給未來的人看的。** 你關掉一條檢查時知道理由，三個月後的接手 session 不知道。台帳的欄位（誰、何時、為什麼、什麼條件下可以移除）就是那個理由的存放處。

**怎麼做**：豁免走顯式清單 [`scripts/gates/exemptions.md`](../scripts/gates/exemptions.md)（一列一條，含到期條件），兩支閘每次執行都會在 notes 印出目前豁免筆數。臨時性的 inline 抑制要帶理由與追蹤點，不准裸寫。

> 該檔尾段另列了「已知但**不算豁免**的設計取捨」——例如文件漂移閘的宣稱掃描只涵蓋 `README.md` 與 `CLAUDE.md`（本檔與閘的 docstring 會為了說明病灶而引用那些過期字串，納入母體會讓閘咬自己的說明文字）。把母體定義寫在台帳旁邊，是為了讓它不會被誤當成隱形旁路。

## 第 6 條：每個機制要指名讀者

**規則**：新增任何檢查時，必須能明確回答：**誰、在什麼時候、透過什麼管道，會看到它的結果？** 答不出來就不要加。答案要寫進機制本身（workflow 的觸發條件、腳本的 README 段落），不是寫在腦子裡。

**為什麼**：這是本 repo 最貴的一課，而且證據就在 repo 裡。

`.github/workflows/pr-checks.yaml` 定義了五個 job：`test`（hello 服務單元測試）、`portability-guard`（禁止 controller 專屬 annotation 與 `storageClassName`，這是本專案的**可攜鐵律**）、`test-ingestion-dags`、`test-spark`、`test-dbt`。內容完全正確，涵蓋面比任何一支 push workflow 都廣，是這個 repo 品質最好的一份 CI 定義。

它的觸發條件是：

```yaml
on:
  pull_request:
    paths: [...]
```

而這個 repo 從第一個 commit 到 2026-08-10，**開過的 PR 數量是 0**——全部直推 main。實測：

```
$ gh run list --workflow pr-checks.yaml --limit 100 | wc -l
0
```

**這份檔案從未執行過一次。** 那條可攜鐵律，從來沒有任何一行 manifest 被它檢查過。

（2026-08-10 已補上 `push:` 觸發，讓它的讀者變成「每一次直推 main 的作者」。）

注意這裡的教訓不是「pr-checks 寫錯了」——它寫得很好。教訓是：**一個機制的價值不等於它的內容品質，而等於「內容品質 × 它真的跑到的機率」**，而第二項在這裡是 0，所以乘積是 0。花在寫那五個 job 上的時間，產出的實際防護是零。

推廣開來，「沒有讀者」有很多種長相，全部等價於不存在：
- 觸發條件對不上實際工作流（本例）
- workflow 被 `disabled_manually`
- 告警送到沒有人訂閱的頻道
- 檢查結果寫進一個 gitignored 的本機檔案（本 repo 最準確的進度紀錄 `.superpowers/sdd/progress.md` 正是如此——它比 README 準得多，但 `.gitignore` 有一行 `.superpowers/`，所以任何接手的人在 clone 之後都讀不到它）
- 規則寫在只有某一個 harness 會載入的檔案裡

**怎麼做**：新機制的 PR 描述（或 commit 訊息）要有一句「讀者＝___」。CI 類的機制，讀者是「每次 push 的作者」就要有 `push:` 觸發且 path filter 涵蓋得到；「只在 PR 時」是合法答案，**但前提是這個 repo 真的會開 PR**。文件類的機制，讀者是「clone 之後會讀到的人」就不能住在 `.gitignore` 裡面。

## 第 7 條：數字要現查，不准寫死在文件裡

**規則**：文件裡出現的**計數與狀態**（幾份 spec、幾支測試、哪個階段做完了、覆蓋率多少），要嘛由腳本現查，要嘛寫死但**同時掛一個會對帳的閘**。裸寫的數字——沒有任何機制在看的數字——一律視為缺陷。

**為什麼**：寫死的數字有兩個性質，合起來很致命：**它一定會過期**，而且**它過期的時候不會有任何跡象**。

過期是必然的，因為數字描述的是會動的東西，而文件不會跟著動。沒有跡象是因為——一個過期的數字看起來跟一個正確的數字一模一樣。「44 份 spec」如果實際是 51 份，讀者沒有任何線索知道要去查。他會直接**拿這個數字當基準做決策**：以為工作量是 A，其實是 B。

比數字更危險的是**狀態宣告**，因為狀態會被當成路由訊號。本 repo 的 `README.md` 首屏寫著「全專案 spec-only、實作待啟動、`docs/plans/` 仍空」。磁碟上的事實是 2 份 plan、19 支 Python、5 張 Gold 表、一整條跑過的 Airflow DAG。這是 public repo 的第一段——**任何人（包括接手的 session、包括看 portfolio 的人）讀到的第一件事就是錯的**，而且錯的方向是「低估已完成的工作」，也就是最傷這個專案目的的方向。

`CLAUDE.md` §目前狀態自稱「此段是本專案的活狀態正本」，卻停在「下一動作＝寫 P1 plan」——而 P1 plan 早就寫完並實作完成。**自稱正本，比不宣稱更糟**：它明確要求讀者信任它，並停止查證。

根源是狀態散在六個載體（README / CLAUDE.md / 兩份 plan 的 checkbox / git log / `.superpowers/sdd/progress.md` / GitHub Actions），其中只有 Actions 是機器產生的，而最準確的那份（progress.md）被 gitignore 了。**多個載體 + 手動同步 = 保證漂移**，這是結構問題，不是紀律問題，光靠「記得更新」解不掉。

**怎麼做**：
1. **收斂載體**：狀態的單一真源是 [`docs/SPEC_STATUS.md`](SPEC_STATUS.md)。README / CLAUDE.md **指向它**，不複述它。
2. **寫死的數字掛 marker**：需要在散文裡寫數字時，用 `<!-- fact:NAME=VALUE -->` 標註，`scripts/gates/check_docs_drift.py` 會現查並比對，不一致就紅。也就是說——**寫死的數字只要有閘現查對帳，就不算漂移風險；沒有閘的才算。** 本文件的規則不是「禁止數字」，是「禁止沒有讀者的數字」（第 6 條的特例）。
3. **一鍵回填**：`python scripts/gates/check_docs_drift.py --write` 會把所有 marker 更新成現查值。數字維護的成本要低到沒有理由不做。
4. **宣告要能被反駁**：不要寫「實作待啟動」這種無法機器驗證又極易過期的句子。要寫，就寫成閘看得懂的形式。

## 附錄：新增一支閘的檢查清單

```
[ ] 1. 有可執行的陽性對照，證明它在該紅時會紅
[ ] 2. 陽性對照斷言的是「錯誤碼」，不只是 exit code != 0
[ ] 3. 所有掃描的母體都有 >0 斷言，且該斷言有自己的錯誤碼
[ ] 4. 無法分類的輸入 → 紅（不是 skip）
[ ] 5. 豁免走顯式清單，筆數會被印出來
[ ] 6. 寫得出「讀者＝___」；CI 的話，觸發條件與 path filter 真的涵蓋得到
[ ] 7. 沒有在文件裡新增裸數字；有數字就掛 fact marker
```
